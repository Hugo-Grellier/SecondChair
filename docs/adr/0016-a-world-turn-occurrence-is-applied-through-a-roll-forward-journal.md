# A world-turn occurrence is applied through a roll-forward journal

Status: proposed — awaiting the GM ([#169](https://github.com/Hugo-Grellier/SecondChair/issues/169))

One world-turn occurrence writes several canon files: the offscreen event, the closed state fact, the new state fact and the knowledge records. A tick then cascades into the threshold steps it crosses. `world._apply` takes one `delegation.act` per change, and each act writes its file and then appends its action log entry. A crash or an exception between two acts leaves the occurrence half-applied: the first changes are written and logged, the rest are missing, and the occurrence record still says `queued`. A crash inside one act, between the file write and the log append, leaves a file with no entry, which `log_hand_edits` later reports as a hand edit. A rerun then plans the same key again on top of a moved clock, and undo walks only the entries the record lists, which here are none. Canon stays human-editable Markdown and YAML, with SQLite derived (ADR 0007), so the fix cannot be a database transaction.

We propose that **a world-turn occurrence, together with every step it cascades into, is applied through one durable intent journal and rolled forward on recovery**. Other multi-change Core operations are a proposed extension (see *Scope*), not part of this decision.

1. **Plan in memory, then check the level, then journal.** Under the workspace lock, compute every change of the tick and of its whole cascade without writing anything. This is not what the code does today, and it is the main implementation cost. `_cascade` reads the clock and the agenda through `_current`, which goes through the index, *after* the tick's files are written, and `_register` writes each new step's occurrence record before applying it. Planning everything first needs a pure successor-state computation: `_current` evaluated over the index *overlaid with the planned changes* (the planned fact documents parsed in memory, the closed facts' new `valid_to`), and the step records built in memory rather than registered. Ids and keys are already deterministic (`_id`, ADR 0009), so the overlay gives the same plan a step-by-step run would. It must use the same as-of date as `_cascade` once [#205](https://github.com/Hugo-Grellier/SecondChair/pull/205) changes which date that is. Then the effective level is checked **once**, for the whole plan, before anything is journaled (the same `living_world` cell and table moment govern every change). If it holds the plan for approval, the occurrence is held whole behind one call, as a tick held at propose is today, and nothing is journaled. A journal therefore never mixes applied and pending entries. `approve` (the GM accepted at once) applies the whole plan.
2. **Write the journal.** One file, `.secondchair/journal/<key-hash>.yaml`, for the tick and its cascade. It holds the tick's key; the Core's package version; an `inputs_digest` (below); and the ordered records it will write. Those are every canon target, with its content before (or `absent`) and after, the log entry each one gets with its id fixed in advance, and every occurrence record the operation writes: each new step record, each step record set to `applied`, and the tick's own record, which is last.
3. **Apply.** Write each record in journal order: canon targets, their log entries, then the step occurrence records, then the tick's record. Each step is idempotent: a target already holding its `after`, or a log entry or occurrence record already present with the journaled content, is skipped.
4. **Commit.** The commit marker is the tick's occurrence record reading `status: applied` with its entries. It is the journal's last record, so it lands only once every canon file, every log entry and every step record before it has landed. The journal file is deleted after it. A journal still present is therefore uncommitted whatever the occurrence records say, and recovery finishes it.
5. **Recover.** On the first, non-reentrant acquisition of `delegation.locked()`, before anything else runs under the lock, the Core looks for leftover journals and rolls each one forward with steps 3 and 4. `log_hand_edits` takes the same lock, so recovery always runs before it. Otherwise a recovered file with no log entry yet would be reported as a hand edit (CAN-11). The index's fingerprint includes `.secondchair/journal/`, so a read that finds a pending journal rebuilds, takes the lock and recovers first rather than serving a half-applied canon. After recovery the index is rebuilt, because the rolled-forward targets changed `canon/` and `action-log/`.

### Durability

Rename is atomic but not durable. Every write in steps 2 to 4 goes through `delegation._write`, which already writes a temporary file and renames it, so a torn target never holds partial content. A torn file would match neither `before` nor `after` and would wrongly stop recovery as a hand edit. `_write` gains an `fsync` of the temporary file before the rename and an `fsync` of its directory after, and the journal file is written with it before step 3 starts. Creating `.secondchair/journal/` fsyncs its parent once. Every Core write gains this, not only journaled ones: it costs two syncs per file on a handful of files per action.

### Stale plans

A journal is data, so rolling it forward replays exactly what was planned, whatever code runs recovery. What can go stale is what the plan read but does not write. `inputs_digest` is a SHA-256 over `workspace.yaml`, `delegation.yaml`, every file under `canon/` and `occurrences/` that is not a journal target, the journal targets' `before` contents, and the action log up to the journal's first entry id. Recovery recomputes the digest the same way. If it matches, the plan still describes the workspace it was made from, and recovery rolls forward. If it differs, a hand edit or another writer changed an input in the meantime, or the Core's package version changed and the GM wants the new code to plan. Recovery then rolls back: each target already at `after` is restored to `before`, and the journal's log entries are marked `undone` with the reason `recovery`. Recovery then opens an exception call on the GM naming the occurrence, and the next world-turn plans it afresh. A version change alone, with an unchanged digest, rolls forward and is noted in the call log.

## Proposed answers

These are the GM's calls on #169. The ADR proposes them; it does not settle them.

- **Roll forward or back?** Forward when the digest matches: the plan was validated against those inputs, so finishing it gives the canon a crash-free run would have. A roll-back is kept for the stale case above.
- **When recovery cannot roll forward.** If a target holds neither its `before` nor its `after` content, something edited it in the meantime, a hand edit or another tool. Recovery stops and keeps the journal, and the occurrence becomes an exception call on the GM that names the file, its three versions and the occurrence. Nothing more is written for it until the GM resolves the file and runs `secondchair recover`.
- **Undo of a partial occurrence.** There is none to undo. After recovery an occurrence is either applied whole, with its cascade, which undo already handles (LW-12), or blocked behind its call with its journal kept.
- **Locks.** There is still one workspace-wide `flock` (`delegation.locked`). The journal does not replace it: it covers a crash, not concurrency. Hand edits are not locked out. They are detected (`log_hand_edits`) and, during recovery, they lead to the stop above.
- **Scope.** The decision covers the world-turn only: every occurrence `world._apply` applies (from `world_turn`, `settle_unless` and `decide`), with its cascade. These are proposed follow-ups, each its own decision: capture consolidation (a fact, then its event, then its knowledge), a scene with its documents, and a single `act`, whose one gap is a file written with no log entry, folded into a one-change journal.

## Considered Options

- **SQLite as the source of truth with transactions**: rejected. It contradicts ADR 0007, since Markdown is canon and is edited by hand.
- **A copy-on-write workspace snapshot per occurrence**: rejected. It costs a copy of the whole workspace for every tick and breaks hand edits made in the meantime.
- **Recover from the occurrence tags already in the action log (no journal)**: the lighter option, and the main alternative. Every entry an occurrence writes already carries `occurrence: <key>` (`delegation.act(..., occurrence=key)`). On recovery, the Core finds entries tagged with a key whose occurrence record is not `applied`. It then either undoes them through the existing undo path, which returns the occurrence to the queue for the next world-turn to plan afresh, or completes them from a fresh plan. It needs no journal and no in-memory successor state, and it reuses undo, so it is much less code. Its trade-offs:
  - *Blind spots.* A file written before its entry (a crash inside `act`) carries no tag; it surfaces as a hand edit. Step occurrence records `_register` wrote and the tick's own record carry no entry. Closing the first gap means appending the entry before writing the file, a change to `act` on every path.
  - *Undo is a GM gesture.* `delegation.undo` logs a GM interaction the GM never made, and it refuses entries from a frozen moment. A crash just before a moment change would strand the occurrence. Recovery needs its own entry kind instead.
  - *Completing* from a fresh plan may write something other than the interrupted run would have, once the canon has moved (a hand edit, #205's as-of date). *Undoing* is safe, but it re-queues a tick whose first effects the Director's Desk may already have shown.
  - It has the same durability needs as the journal (fsync, temp-and-rename, recovery before `log_hand_edits`).

  We recommend the journal for the world-turn, because the cascade is where all four trade-offs bite at once: several occurrence records, several moments of exposure, and a plan that depends on the state it writes. The tag scan is the right tool if the GM wants the cheaper fix now. In that case this ADR becomes "undo by tag, entry before file", the in-memory successor state is not needed, and the journal stays the upgrade path.
- **Roll back on every recovery**: rejected, see *Roll forward or back*. It is kept for stale plans only.

## Consequences

- `world._apply` and `_cascade` become a planner (the pure successor-state overlay of step 1) and one `delegation.apply_journal(ws, plan)`. The level check moves out of the per-change `delegation.act` into one check before the journal. The log entries keep the fields `act` writes today, so undo (LW-12) and the Director's Desk read them unchanged.
- `delegation._write` fsyncs the file and its directory. `delegation.locked()` runs recovery on first acquisition. The index fingerprint includes `.secondchair/journal/`.
- New workspace directory `.secondchair/journal/`, in the workspace layout contract. It is state, not canon: deleting `.secondchair/` while a journal is pending loses the roll-forward, and the next `check` reports the half-applied occurrence as hand edits.
- **Fault-injection test plan.** A test hook raises at step *k*, for every *k*, across one tick with a threshold cascade of two steps: before the journal, after the journal, after each target write, after each log append, after each step record, after the tick's record, and before the journal is deleted. For each *k*, recovery must produce a workspace byte-identical (canon, action log, occurrences) to an uninterrupted run, a second recovery must change nothing, and no hand edit may be logged. Further cases:
  - a torn target (a `.tmp` left behind);
  - a hand edit to a journal target between the crash and recovery: an exception call, with the journal kept;
  - a hand edit to a non-target input (a digest mismatch): rolled back, with a call;
  - a read before any write: the index rebuilds through recovery;
  - a plan held at propose: nothing journaled;
  - a subprocess killed with SIGKILL during a real world-turn;
  - two Core processes racing: the second waits on the lock, then finds nothing to recover.
